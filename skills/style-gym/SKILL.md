# Style gym

An optional experiment loop using existing Style and generation tools. Adapt it to the task. Read [the MCP contract](../asset-generator/references/mcp-contract.md) before workspace calls or generation: select an accessible brand with `list_brands`, pass explicit `brandId` on every call, and preserve durable job identity through retries. Account OAuth has no sticky workspace; null/omitted is personal, and legacy scoped credentials cannot switch.

For hero images, CTA backgrounds, cards, or other imagery that must work inside an interface, read [Placement composition](references/placement-composition.md). It covers separating reusable treatment from layout, art-directed mobile images, and reviewing the result with real copy.

1. Read the current brand guide and call `list_styles` in the intended workspace. Use its existing categories, names and thumbnails to place the candidate in context; inspect nearby Styles with `get_style` and `list_assets` filtered by their IDs. Inspect the actual reference assets. Define the visual traits to keep and what must vary between generations.
2. Choose a small set of different briefs before optimizing: one close to the reference and at least one new subject or composition. Keep model, quality, dimensions, and reference order fixed for comparisons.
3. Draft a compact reusable Style prompt. Put scene-specific instructions in the generation prompt. When ordered inputs are exposed, keep official logos in returned version-pinned brand inputs rather than describing a substitute.
4. If authorized to create Styles in the workspace, create a distinctly named candidate with `create_style` **before generating its examples**. Pass the appropriate existing `category` (follow the user's explicit category choice), and record its ID. Do not create a near-duplicate category or overwrite a shared Style just to run an experiment. Otherwise keep the candidate local and explain that it is not yet in the shared library.
5. Generate examples with that exact `styleId` and `brandId`; keep subject-specific instructions in `prompt`. Use a fresh UUID `requestId` per intended example, retain the returned `jobId`, and poll `get_generation_status` in the same workspace until terminal. Transport retries use the same ID and identical arguments; unknown outcomes and poll timeouts prove neither failure nor a refund. Pasting the Style's text into a Freestyle prompt does not associate the image with the saved Style. Download and visually inspect outputs. Compare fidelity, response to the brief, diversity, logo/text accuracy, and practical usability. Record failures as well as successes; one matching output is not proof of a broadly useful Style.
6. Change one meaningful variable, rerun the same briefs, and keep the stronger version. Use returned receipt IDs and, when exposed, `get_generation_details` as evidence of settings. Provider results can vary even with identical settings.
7. Finish the shared library entry: choose a representative successful example, read the Style's current `updatedAt` with `get_style`, and call `set_style_thumbnail` with its `assetId` and `expectedUpdatedAt`. This changes the sidebar thumbnail only, not generation references. Confirm `get_style` returns the intended category/thumbnail and `list_assets` filtered by the Style ID contains its examples. Report a conflict and refresh instead of blindly retrying a changed Style.
8. Present the selected examples and limitations. Keep experiment notes with the project: brief, source links, candidate Style IDs, asset/receipt IDs, actual settings, observations, and next test. This lets another agent continue without the original chat.

Discover supported fields/tools first. Older servers may omit category/thumbnail metadata or `set_style_thumbnail`; explicitly report an unfinished library entry rather than sending unsupported fields or claiming it is complete. Existing Freestyle exploration images retain that historical provenance when a Style is saved later. Do not rewrite immutable receipts to make them appear generated by that Style.

Existing MCP `create_style` authors text-based Styles. Reference-set editing and formal Style-fork lineage are not exposed by that tool yet. Do not silently claim a text-only candidate has saved image references or ancestry. The tools can be composed directly without following this loop.
